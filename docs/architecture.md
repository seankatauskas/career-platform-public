# Job-search deterministic core

This document freezes the v1 implementation boundary for the private, Mac-local
application tracker. The event ledger and service own all mutations. The dashboard,
workers, Outlook connector, browser extension, local classifiers, and future Hermes
client must not write SQLite directly.

## Public boundary

`job_search.contracts` is the source of truth for event names, phases, terminal
outcomes, action kinds, payload canonicalization, service protocols, Outlook transport,
and classifier isolation. Loopback HTTP uses `/api/v1`; Python callers use the matching
service methods. Every mutation includes an idempotency key, actor kind, source kind,
and optional source reference.

All timestamps crossing the boundary are second-precision UTC strings ending in `Z`.
All JSON is NFC-normalized, finite, sorted-key compact JSON. Exact action approvals are
SHA-256 hashes of that encoding and expire after 15 minutes.

The application database is separate from `job-boards.db`. It is created with mode
`0600`, uses WAL, foreign keys, a 10-second busy timeout, and `synchronous=FULL`.
Migrations are ordered, checksummed, transactional, and never routed through
`job_search/collection/boards.py`. Application events are append-only and projections are rebuildable.

## Integration contracts

- Shortlists are generated by `job_labeler.policy_recommendations()` and exposed through
  an idempotent wrapper that records one explicit session and its impressions.
- Existing applications are supplied as concrete `(ats, job_id)` exclusions. The
  preference layer maps them through current family membership; it never opens
  `job-search.db`.
- `submission_observed` creates exactly one `recommendation.applied` outbox item. The
  sink stores its application event ID as `recommendation_feedback.source_event_id` so
  retries cannot duplicate passive feedback.
- Outlook tokens remain inside the auth/transport adapter. Workers use silent auth only.
  Recruiter replies can be sent only from immutable, explicitly approved career action proposals. Personal calendar commitments carry no attendees; accepting invitations remains unsupported.
- Personal Outlook calendar availability uses paged `calendarView`, because delegated
  personal accounts do not support `getSchedule`. Privacy-minimized agenda snapshots retain busy intervals and career-event context for briefings.
- Classifiers receive sanitized text plus at most 20 candidate applications and return
  strict JSON. They have no tools, network, tokens, SQL, or mutation access.

## Parallel ownership

Task worktrees must start from the contract commit and stay within these boundaries:

| Lane | Exclusive paths |
|---|---|
| Ledger | `job_search/db.py`, `reducer.py`, `store.py`, `service.py`, ledger tests |
| Outlook | `job_search/outlook/`, Outlook fixtures/tests |
| Mail intelligence | `job_search/mail/`, classifier fixtures/tests |
| Dashboard | `job_search/web/`, `job_search/dashboard.py`, dashboard assets/tests |
| Automation | `job_search/scheduler.py`, `worker.py`, `launchd/`, automation tests |
| Scheduling | `job_search/availability.py`, `actions.py`, scheduling tests |
| Orchestrator | contracts, preference compatibility, shared schema/API changes, docs |

Agents request contract changes from the orchestrator rather than editing
`contracts.py`. Generated OpenWiki pages are not edited by hand.

## Implemented runtime

The deterministic core, loopback dashboard, Outlook sync, mail proposal pipeline,
availability planner, approved-action saga, SQLite scheduler, bounded worker, and Hermes
capability adapter are implemented. Operational setup and failure behavior are in
`docs/operations/job-search-runbook.md`. The worker owns the four-hour ATS cadence and five-minute local
processing cadence. `job_search.runtime` composes independent core/model lanes and the
lineage-bearing opportunity DAG; stable recommendation watermarks do not wait for the
low-priority salary branch. Details are in `docs/operations/job-search-runtime.md`.

The all-history encrypted mail and temporal-scheduling path is composed into the core
worker and documented in `docs/operations/job-search-secure-mail.md`. Mailbox discovery stores only
folder identifiers and excludes Junk, Deleted Items, and both descendant subtrees.
Secure task results contain counts, never Graph tokens or raw content. Hermes remains
replaceable and cannot approve or execute actions through model tools. A separate trusted Telegram interaction handler accepts owner button presses and exact preview approvals before model processing.

The Hermes surface is assembled from injected Protocols rather than database or Outlook
objects. A loopback bearer-authenticated MCP adapter exposes only its frozen tool
registry. Migration 6 adds independent general reminders and a notification outbox;
generic publish/claim/complete service methods let mail, application, reminder,
system-health, and opportunity streams share durable delivery without making Hermes a
ledger writer. Phone delivery is a fixed absolute-Hermes `send --to` argv with bounded
plain text on stdin. Interactive attention cards use the trusted Telegram delivery adapter and durable receipts. Both transports remain injectable in offline tests.

The chief-of-staff services add attention decisions, daily briefings, approved recruiter replies,
and personal calendar commitments (migrations 16–18). See
[Hermes chief of staff](hermes-chief-of-staff.md) for defaults, controls, and delivery recovery.

## Resume laboratory boundary

The optional resume laboratory is a sidecar to the application ledger. It owns
immutable user-authored baseline resume versions, exact TeX/PDF/text artifacts,
per-job ATS-proxy evaluations, grounded rewrite approvals, synthetic benchmarks, and
append-only application selections. The application ledger remains authoritative for
lifecycle state and is referenced only through `application_id`; resume state does not
add event types or mutable columns to the frozen ledger.

Preparing an application scores every active hand-written baseline first. The highest
ranked baseline remains the primary recommendation and anchors a grounded rewrite and
an explicitly synthetic exaggerated comparison. Independent market-ideal and
adversarial variants provide reference ceilings. Only active user-authored baselines
and approved grounded rewrites can be selected for a real application.

The scanner evaluates the rendered PDF through a versioned hybrid pipeline. Local-LLM
output is limited to source-grounded requirement extraction and ambiguous evidence
classification; deterministic code owns parsing gates, exact/Boolean matching,
eligibility separation, feature weights, and the final score. See
`docs/models/ats-proxy-model.md` for score semantics and inference limits.
